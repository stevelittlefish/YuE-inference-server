A field guide to the inference pipeline

Inside YuE2.
From words to waveform.

A song passes through several different representations before you can hear it. Here’s what each one does, how they connect, and where you can look inside.

Follow the flowchartWalk through the stagesInspect the outputsTry it in code

Think: brief → composition → music codes → acoustic detail → recording. The early stages describe what to play; the later stages build a sound representation and turn it into audio. Learned models connect these representations.

We can inspect the architecture, code, inputs and intermediate outputs. Interpreting exactly what an individual learned weight “knows” is a different problem.

The whole journey

Follow the arrows downward. Select a planning mode to see where the route changes. Each main box links to its explanation below.

Code / tokenizer · no inferenceModel 1 · YuE2-3B (AR and NAR)Model 2 · YuE2-Vae decoder

AR = autoregressive: generate one token at a time. NAR = non-autoregressive: update acoustic positions together within a chunk. Stage 5 first uses the AR path to cache conditioning, then the NAR path during flow matching. The planning selector changes stage 3; stages 4–6 keep their model roles in every route.

The default full route generates a melody-and-chord score before music tokens. You can also supply a score or skip symbolic planning altogether.

What happens at each stage?

1

Receive the brief and wait for the GPU

You send style, lyrics and options to POST /v1/generate. The server checks the request, creates a job directory and puts the job into a queue. It returns a job ID immediately.

Like handing a brief to a studio and receiving a booking number.

What exists now: a validated request and a queued job.

Under the hood · scheduling and startup

One worker thread processes jobs serially. A GPU lock prevents generation and parking from moving the weights at the same time. The queue and job registry live in memory. Clients poll the job endpoint, then download completed artifacts.

At startup, the server resolves model files, verifies integrity, loads the main model onto the selected device, and loads the VAE decoder into CPU memory before serving. If the HTTP request omits the seed, the runner chooses and records one.

Read: server.py · worker.py · pipeline_runner.py

2

Translate the brief into the model’s input format

The pipeline combines a generation instruction, your style description and your lyrics into a text prompt. A text tokenizer converts it into integer IDs. Special markers separate the score and music regions.

Instruction: generate a score, then music
[Tags]
warm piano, acoustic pop, female vocal
[Lyrics]
[Verse]
Your words here…

<abc> …score tokens… </abc>
<music> …music tokens… </music>

Illustrative layout. The real input is a sequence of integer token IDs, including dedicated boundary IDs.

What moves forward: text tokens and instructions about which content to generate.

Under the hood · tokenization and boundaries

The text/ABC tokenizer uses the checkpoint’s qwen.tiktoken vocabulary. Ordinary text, ABC boundaries and music codes occupy distinct parts of the model’s vocabulary. Input text is normalized to Unicode NFC.

Read: protocol.py · tokenization_yue2.py

3

Compose a score you can actually inspect

With cot="full", the model writes ABC notation for melody and chords. With "melody", it writes a melody-only score. With "off", it skips this composition step. Supplying your own ABC bypasses score generation.

ABC is a textual music notation for notes, durations, meter, tempo and other musical information. This makes the intended composition visible and editable before a recording is made.

Like a composer handing a score to the performers.

What moves forward: the original text plus the exact score token IDs, if a score is used.

Under the hood · what “planning” means here

The same autoregressive model used in the next stage generates the ABC text, one token at a time. Here, the cot option selects a symbolic music plan. The score is learned conditioning for the audio generation; it is not rendered by a conventional MIDI synthesizer.

To edit a saved score, copy its ABC and submit the edited text as a new abc input. Loading an unchanged saved plan preserves exact tokens and verifies its files. A changed score produces a new recording; unchanged passages need not retain identical singing or timbre.

Read: pipeline.py → plan() · editing.md

4

Choose a sequence of learned music codes

The model now predicts discrete music codes one at a time. Every new choice depends on the prompt, the score when present, and the music codes already chosen.

There are 32,768 possible codes. A code is a learned representation, not a written note or a waveform sample. Looking at its integer ID alone won’t tell you what it sounds like.

A rough analogy: choosing a sequence of compressed musical building blocks. Their meaning is learned, rather than listed in a human-readable dictionary.

What moves forward: a one-dimensional integer array, saved as semantic.npy.

Under the hood · sampling, caching and guidance

Each step masks out invalid token types, applies a recent-token repetition penalty, temperature, top-k and top-p filtering, then samples a token. Temperature zero chooses the highest-scoring token. A request-local random generator uses the seed.

Attention keys and values are cached, so earlier tokens do not need to be fully recomputed at each step. Optional classifier-free guidance combines predictions from positive and negative conditioning branches. The default guidance is 1.0 with symbolic planning and 1.01 with planning off.

Generation stops at the music end marker or the configured token limit. Hitting the limit is recorded as truncation. The default music budget is 9,000 tokens, and the model context is 24,576 tokens.

Read: sampling.py · pipeline.py → generate_semantic()

5

Turn noise into a continuous sound representation

The pipeline draws a block of random noise. Guided by the music codes and conditioning prefix, a learned acoustic model repeatedly transforms that block into audio latents: a compact, continuous representation of sound.

The default is 32 flow-matching integration steps. Positions within an acoustic chunk are processed together, rather than chosen one at a time.

Think of gradually shaping a block of material into a detailed performance. The numerical solver follows directions predicted by the model.

What moves forward: an array shaped [T, 64] — 64 numbers for each frame, saved as latent.npy.

Under the hood · flow matching and the two model paths

The noise has one 64-dimensional vector per music code. A midpoint ODE solver follows the predicted velocity field, using two model evaluations per integration step: 64 velocity evaluations per chunk at the default setting.

Long sequences are split into chunks that fit the context. The fixed autoregressive conditioning is processed once per chunk; its keys and values are reused throughout the solver. The acoustic positions can attend across the chunk and to the cached conditioning.

The main model is an AR–NAR Mixture-of-Transformers. Each layer has separate attention projections and feed-forward networks for the autoregressive (one token at a time) and non-autoregressive (positions processed together) paths. The score and music-token stages use the AR path; acoustic synthesis uses the NAR path conditioned on the AR cache.

Read: nar.py · modeling_yue2.py → DecoderLayer

6

Expand the latents into a playable waveform

A separate VAE decoder turns the latents into 48 kHz stereo audio. Its convolutional layers expand the time resolution until there is a left and right sample stream you can play.

The pipeline decodes manageable tiles with extra neighboring context, retaining the central output of each tile. This keeps memory use bounded while providing the context needed near tile edges.

What comes out: a waveform array shaped [audio samples, 2], then a FLAC or WAV file.

Under the hood · time resolution and memory

The default decoder expands each latent frame by a factor of 1,920, corresponding to about 25 latent frames per second at 48 kHz. Its natural waveform length is 1920 × T − 64 samples.

Before decoding, the main model moves to CPU and the VAE decoder moves onto the selected device. The decoder runs in float32. The pipeline uses 1,024-frame cores by default, or 512 at a memory budget of 12 GiB or less, with a 16-frame halo. It crops the outputs rather than crossfading them. The completed waveform is checked for finite values and clamped to [-1, 1]. The decoder returns to CPU afterward.

Read: modeling_vae.py · pipeline.py → decode()

Where does the “AI” actually happen?

In score prediction, music-code prediction, acoustic velocity prediction and waveform decoding. The surrounding Python controls prompts, sampling, numerical integration, memory movement, file writing and job handling. Those control decisions are all visible in this repository.

The evidence left behind

A completed audio job saves the intermediate representations as well as the recording. These are the places to look when you want to understand a particular run.

Pause the pipeline between stages

The Python interface exposes each boundary directly. This example runs the stages separately and prints the sizes of the intermediate representations.

from yue2 import YuE2Pipeline
import soundfile as sf

with YuE2Pipeline.from_pretrained("m-a-p/YuE2-3B") as pipe:
    plan = pipe.plan(
        style="warm piano, acoustic pop, female vocal",
        lyrics="[Verse]\nYour lyrics here…",
        cot="full",
        seed=42,
    )
    print(plan.abc)                      # Read the composition
    plan.save("outputs/exploration-plan")

    semantic = pipe.generate_semantic(plan)
    print(len(semantic.tokens))          # Count music codes

    latents = pipe.synthesize(semantic)
    print(latents.shape)                 # (T, 64)

    audio = pipe.decode(latents)
    print(audio.shape)                   # (samples, 2)
    sf.write("outputs/exploration-plan/audio.wav", audio, 48000)

This is an executable outline, not a recorded generation. It requires the project dependencies and model files; the supported starting point is a BF16-capable NVIDIA GPU with about 24 GB VRAM. For the complete metadata bundle, use the normal song = pipe(...) call followed by song.save_artifacts(...).

Change the composition

Copy the ABC, edit a chord or melody, then submit it as a new abc input. Keep the style, lyrics and seed fixed to make the comparison easier to interpret.

Isolate the decoder

Keep the latents fixed and decode them with the standard and legacy VAE releases. This compares decoding while keeping the upstream generation unchanged.

A few useful distinctions

A score is a plan, not the recording. Changes influence a newly generated performance. They do not guarantee sample-identical audio in untouched passages.

A music code is not a note. The model predicts learned IDs; the acoustic model uses those IDs to construct a continuous representation.

Latents are not waveform samples. They become playable only after the VAE decoder expands them.

The HTTP service is asynchronous, not live audio streaming. Its worker completes the pipeline and publishes files for download.

A playable file can still be truncated. Check the flags in result.json to see whether score or music generation reached a limit.
